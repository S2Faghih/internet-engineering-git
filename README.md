## سؤال ۱: تفاوت merge و rebase

هر دو دستور `git merge` و `git rebase` برای ترکیب تغییرات شاخه‌های مختلف استفاده می‌شوند اما روش انجام این کار و تأثیر آن‌ها بر تاریخچه commitها متفاوت است.

**دستور `git merge`:**

این دستور تغییرات دو شاخه را با هم ترکیب یا همان merge می‌کند. در حالتی که تاریخچه دو شاخه از هم جدا شده باشد، یعنی تا یک commit مشترک بوده‌اند و بعد دو شاخه جدا شده‌اند، معمولاً یک merge commit جدید ایجاد می‌شود که دو والد دارد چون دو شاخه مجزا هستند و نشان می‌دهد تغییرات دو شاخه در چه نقطه‌ای ادغام شده‌اند. در این روش، commitهای قبلی شاخه‌ها بازنویسی نمی‌شوند یعنی همان کامیت‌ها برای هر برنچ حفظ و صرفا در یک نقطه با هم ادغام شده‌اند.

مثلا اگر بخواهیم تغییرات شاخه `feature` را وارد `main` کنیم دستور زیر را می‌زنیم که تصویر تاریخچه دو نمونه برنچ را هم قرار دادم:

```bash
git switch main
git merge feature
```

البته اگر امکان fast-forward وجود داشته باشد، merge می‌تواند بدون ایجاد commit جدید انجام شود. یعنی اگر برنچ مقصد هیچ commit جدیدی نسبت به نقطه‌ مشترک دو برنچ نداشته باشد، Git فقط اشاره‌گر برنچ مقصد را به آخرین commit برنچ مبدأ منتقل می‌کند.

**دستور `git rebase`:**

در این روش، commitهای اختصاصی یک شاخه روی آخرین commit شاخه مبنا دوباره اعمال می‌شوند. در نتیجه، عملا تاریخچه معمولاً خطی‌تر می‌شود و انگار تغییرات شاخه feature از ابتدا روی آخرین نسخه main انجام شده‌اند.

برای مثال:

```bash
git switch feature
git rebase main
```

با این دستور، commitهای شاخه feature روی آخرین وضعیت main بازسازی می‌شوند. چون مبنای commitها تغییر می‌کند، شناسه آن‌ها هم تغییر خواهد کرد که مثالی از آن در تصویر زیر است:

**جمع‌بندی:**

تفاوت اصلی این است که merge معمولاً ساختار شاخه‌ای تاریخچه را حفظ می‌کند اما rebase با بازنویسی commitها تاریخچه را خطی‌تر می‌کند. برای شاخه‌های مشترک، merge انتخاب مطمئن‌تری است چون merge کامیت‌های قبلی را بازنویسی نمی‌کند. برای مرتب کردن تاریخچه شاخه شخصی، rebase مناسب است. بهتر است روی commitهایی که دیگران هم از آن‌ها استفاده می‌کنند rebase انجام نشود، چون شناسه آن‌ها تغییر می‌کند و ممکن است هماهنگی تاریخچه افراد به مشکل بخورد.

## سؤال ۲: انتخاب بخشی از تغییرات

در خروجی `git diff`، یک hunk به بخشی از تغییرات گفته می‌شود که معمولاً شامل چند خط اضافه‌شده، حذف‌شده یا ویرایش‌شده به همراه تعدادی خط اطراف آنهاست. Git تغییرات را به این بخش‌ها تقسیم می‌کند تا بررسی تفاوت نسخه‌ها ساده‌تر شود.

اگر در یک فایل چند تغییر مستقل انجام داده باشیم، ممکن است نخواهیم همه آن‌ها را در یک commit قرار دهیم. برای این کار می‌توانیم از دستور زیر استفاده کنیم:

```bash
git add -p README.md
```

گزینه `-p` یا `--patch` باعث می‌شود Git تغییرات فایل را به‌صورت تعاملی و بخش‌به‌بخش نمایش دهد و درباره اضافه کردن هر hunk به staging از ما سؤال کند.

مهم‌ترین گزینه‌های این حالت عبارت‌اند از:

- گزینه `y`: بخش فعلی به staging اضافه می‌شود.
- گزینه `n`: بخش فعلی اضافه نمی‌شود.
- گزینه `s`: تلاش می‌کند بخش فعلی را به قسمت‌های کوچک‌تر تقسیم کند.
- گزینه `e`: امکان ویرایش دستی patch را فراهم می‌کند.
- گزینه `q`: از حالت تعاملی خارج می‌شود.
- گزینه `?`: راهنمای گزینه‌ها را نشان می‌دهد.

مثلا فرض می‌کنیم در یک فایل هم توضیحات را اصلاح کرده‌ایم و هم یک مثال جدید نوشته‌ایم، ولی فعلاً فقط می‌خواهیم اصلاح توضیحات را commit کنیم. با اجرای `git add -p`، برای بخش مربوط به توضیحات گزینه `y` و برای مثال جدیدی که نوشتیم، گزینه `n` را انتخاب می‌کنیم.


فایده این روش این است که هر commit می‌تواند مربوط به یک تغییر مشخص باشد. بنابراین با این روش تاریخچه پروژه قابل‌فهم‌تر می‌شود و اگر بعداً لازم باشد یک تغییر را بررسی کنیم یا برگردانیم، این کار ساده‌تر خواهد بود.

## سؤال ۳: پیدا کردن منشأ خطا با git bisect

دستور `git bisect` برای پیدا کردن commitای استفاده می‌شود که یک خطا از آن وارد پروژه شده است. این دستور با روش جست‌وجوی دودویی کار می‌کند یعنی به‌جای بررسی تمام commitها به ترتیب، در هر مرحله حدود نیمی از محدوده جست‌وجو را کنار می‌گذارد.

برای استفاده از این دستور، اول باید یک commit سالم و یک commit معیوب را بشناسیم. فرض می‌کنیم آخرین commit پروژه دارای خطاست ولی می‌دانیم در یک commit قدیمی‌تر این خطا وجود نداشته است.

ابتدا دستور زیر را اجرا می‌کنیم:

```bash
git bisect start
```

سپس commit معیوب را مشخص می‌کنیم:

```bash
git bisect bad HEAD
```

در اینجا `HEAD` به commit فعلی اشاره می‌کند.

بعد یک commit سالم را که می‌دانیم تا آنجا خطا وجود نداشته، با مثلا شناسه فرضی زیر معرفی می‌کنیم:

```bash
git bisect good a1b2c3d
```

حالا Git به‌صورت خودکار یک commit در میانه محدوده انتخاب می‌کند و working tree را روی آن نسخه قرار می‌دهد. در این مرحله باید پروژه را بررسی کنیم و آزمایش مربوط به خطا را انجام دهیم.

اگر خطا وجود داشته باشد:

```bash
git bisect bad
```

اگر خطا وجود نداشته باشد:

```bash
git bisect good
```

با هر بار مشخص کردن نتیجه، Git بازه جست‌وجو را کوچک‌تر می‌کند و commit دیگری را برای بررسی انتخاب می‌کند. این مراحل را ادامه می‌دهیم تا Git اولین commit معیوب را شناسایی کند.

در پایان، با دستور زیر از حالت bisect خارج می‌شویم:

```bash
git bisect reset
```

تصویر زیر مفهوم را واضح‌تر منتقل می‌کند. کاربر می‌داند تا کامیت C خطا نبوده اما در کامیت L خطا وجود دارد:

**مثال کاربردی:**

مثلا در یک پروژه وب، دکمه ورود کاربران قبلاً درست کار می‌کرده اما در نسخه فعلی با کلیک روی آن خطا رخ می‌دهد. اگر در این فاصله تعداد زیادی commit ثبت شده باشد، بررسی تک‌تک آنها برای پیدا کردن شروع خطا زمان‌بر است. با git bisect می‌توانیم نسخه‌های میانی را آزمایش کنیم تا مشخص شود مشکل از کدام commit شروع شده است.

مزیت این روش کاهش تعداد آزمایش‌ها است. برای مثال، اگر 100 commit در محدوده جست‌وجو داشته باشیم،چون این روش از جست‌وجوی دودویی استفاده می‌کند و با هر مرحله نصف commitهای باقی‌مانده حذف می‌شوند، بنابرین در حالت معمول تقریباً $\log_2(100) \approx 7$ مرحله بررسی کافی است. ولی البته این روش زمانی نتیجه قابل‌اعتماد می‌دهد که بتوانیم سالم یا معیوب بودن نسخه‌های مختلف را به‌درستی تشخیص دهیم.

## سؤال ۴: بررسی تغییرات پیش از commit

**بخش اول: بررسی وضعیت و تغییرات**

برای مشاهده وضعیت کلی مخزن از دستور زیر استفاده می‌کنیم:

```bash
git status
```

این دستور مشخص می‌کند چه فایل‌هایی تغییر کرده‌اند، کدام تغییرات وارد staging شده‌اند و چه فایل‌هایی هنوز untracked هستند.

برای مشاهده تغییراتی که در working tree وجود دارند ولی هنوز به staging اضافه نشده‌اند، از دستور زیر استفاده می‌کنیم:

```bash
git diff
```

برای مشاهده تغییراتی که قبلاً به staging اضافه شده‌اند و برای commit بعدی آماده هستند، دستور زیر را اجرا می‌کنیم:

```bash
git diff --cached
```

گزینه `--cached` همان کاربرد `--staged` را دارد.

تفاوت این دو دستور این است که `git diff` نسخه فعلی working tree را با staging مقایسه می‌کند، در حالی که `git diff --cached` تغییرات staging را نسبت به آخرین commit نشان می‌دهد. بنابراین با توجه به صورت سوال، چون فایل `README.md` بعد از stage شدن دوباره ویرایش شده است، ممکن است هر دو دستور تغییراتی را برای این فایل نشان دهند.

**بخش دوم: نتیجه commit معمولی**

اگر در این وضعیت مثلا دستور زیر را اجرا کنیم:

```bash
git commit -m "Update README"
```

فقط تغییراتی که قبلاً وارد staging شده‌اند در commit قرار می‌گیرند. ویرایش‌هایی که بعد از آخرین `git add` انجام شده‌اند، وارد این commit نمی‌شوند و در working tree باقی می‌مانند. دلیل این رفتار این است که Git موقع commit معمولی، محتوای staging را ثبت می‌کند نه تمام تغییرات موجود در working tree را. برای وارد کردن ویرایش‌های جدید به commit لازم است دوباره `git add` اجرا شود، اما در این سؤال فرض شده چنین کاری انجام نداده‌ایم پس تغییرات جدید وارد کامیت نمی‌شوند.

**بخش سوم: نادیده گرفتن فایل‌های موقت**

برای جلوگیری از اضافه شدن فایل‌های پوشه `tmp/` به commitهای بعدی، باید در ریشه پروژه فایلی به نام `.gitignore` ایجاد کنیم و خط زیر را داخل آن قرار دهیم:

```gitignore
/tmp/
```

این الگو باعث می‌شود Git فایل‌های untracked داخل این پوشه را نادیده بگیرد و هنگام اضافه کردن معمول فایل‌ها به staging، آنها را وارد نکند. البته این تنظیم برای فایل‌هایی که از قبل tracked بوده‌اند کافی نیست. فایل‌هایی که Git قبلاً دنبال می‌کرده، با اضافه شدن به `.gitignore` به‌صورت خودکار از tracking خارج نمی‌شوند.

اگر بخواهیم فایل tracked را از tracking خارج کنیم ولی نسخه محلی آن را نگه داریم، می‌توانیم از دستور زیر استفاده کنیم:

```bash
git rm --cached path/to/file
```

برای یک پوشه شامل فایل‌های tracked هم می‌توان از دستور زیر استفاده کرد:

```bash
git rm -r --cached tmp/
```

این دستور فایل‌های پوشه را از index خارج می‌کند اما نسخه محلی آن‌ها را حذف نمی‌کند. پس از commit کردن این تغییر و تنظیم `.gitignore`، فایل‌های پوشه در تغییرات بعدی نادیده گرفته می‌شوند.

## سؤال ۵: رفع merge conflict در کار گروهی

**بخش اول: دلیل ایجاد conflict**

در این سناریو، هر دو نفر از یک commit مشترک شروع کرده‌اند و یک خط از فایل `README.md` را به دو شکل متفاوت تغییر داده‌اند. هنگام merge کردن برنچ‌ها، Git نمی‌تواند به‌صورت خودکار تصمیم بگیرد کدام متن باید در نسخه نهایی قرار بگیرد بنابراین merge conflict رخ می‌دهد. ولی هر تغییری که دو نفر در یک فایل انجام دهند الزاماً باعث conflict نمی‌شود. مثلا اگر دو نفر قسمت‌های جدا از هم یک فایل را تغییر دهند (یعنی مثلا دقیقا یک خط را تغییر ندهند) و Git بتواند تغییرات را بدون هیچ ابهامی ترکیب کند، merge به‌صورت خودکار انجام می‌شود و conflictای هم رخ نمی‌دهد.

**بخش دوم: شناسایی فایل‌ها و متن‌های دارای conflict**

فرض می‌کنیم می‌خواهیم شاخه `feature-description` را وارد شاخه `main` کنیم:

```bash
git switch main
git merge feature-description
```

اگر conflict رخ دهد، می‌توانیم با دستور زیر فایل‌های درگیر را پیدا کنیم:

```bash
git status
```

برای نمایش فقط نام فایل‌های دارای conflict هم از دستور زیر استفاده می‌کنیم:

```bash
git diff --name-only --diff-filter=U
```

حرف `U` نشان‌دهنده فایل‌های دارای تغییرات حل‌نشده است.

در فایل متنی، Git معمولاً علامت‌هایی به نام conflict markers قرار می‌دهد. برای مثال:

```text
<<<<<<< HEAD
This project explains Git commands.
=======
This project contains practical Git examples.
>>>>>>> feature-description
```

قسمت بین `<<<<<<< HEAD` و `=======` مربوط به نسخه شاخه فعلی، یعنی main است.

قسمت بین `=======` و `>>>>>>> feature-description` مربوط به تغییرات شاخه‌ای است که در حال merge آن هستیم.

این علامت‌ها مشخص می‌کنند کدام بخش از فایل نیاز به تصمیم‌گیری و اصلاح دستی دارد.

**بخش سوم: رفع conflict و تکمیل merge**

خود Git نمی‌تواند تصمیم بگیرد کدام تغییر از نظر منطقی درست است پس حل conflict یعنی خودمان باید نسخه نهایی را مشخص کنیم.

چون اطلاعات هر دو تغییر باید حفظ شود، بخش‌های دارای conflict را بررسی می‌کنیم تا مشخص شود هر شاخه چه تغییری داده است بعد با توجه به محتوای دو نسخه متن را اصلاح می‌کنیم. اگر دو تغییر با هم سازگار بودند، می‌توانیم دو توضیح را در یک جمله قرار دهیم یا هرکدام را در یک قسمت جداگانه از README بنویسیم. اگر ناسازگار بودند هم که باید با هماهنگی هم‌تیمی درباره متن نهایی تصمیم بگیریم.
باید فایل `README.md` را باز کنیم و دو متن را به شکلی مناسب با هم ترکیب کنیم. برای مثال، می‌توانیم متن نهایی را این‌گونه قرار دهیم:

```text
This project explains Git commands and contains practical Git examples.
```

در این حالت اطلاعات هر دو متن حفظ شده است.

بعد از اصلاح فایل، باید تمام conflict markerها، یعنی `<<<<<<<`، `=======` و `>>>>>>>` را از بخش‌های دارای conflict حذف کنیم.

برای بررسی وضعیت فایل از دستور زیر استفاده می‌کنیم:

```bash
git diff --check
```

این دستور می‌تواند برخی خطاهای مربوط به قالب‌بندی و باقی ماندن conflict markerها را شناسایی کند. با این حال، برای اطمینان بیشتر، فایل را هم بررسی می‌کنیم تا هیچ علامت مربوط به conflict در متن نهایی باقی نمانده باشد. سپس فایل اصلاح‌شده را به staging اضافه می‌کنیم:

```bash
git add README.md
```

با اجرای دستور زیر بررسی می‌کنیم که دیگر فایلی در وضعیت unresolved باقی نمانده باشد:

```bash
git status
```

اگر تمام conflictها رفع شده باشند، می‌توانیم عملیات merge را با دستور زیر تکمیل کنیم:

```bash
git merge --continue
```

در این مرحله Git عملیات merge را تکمیل می‌کند و در این سناریو یک merge commit ایجاد می‌شود. از آخر هم وضعیت مخزن را بررسی می‌کنیم تا مطمئن شویم عملیات merge کامل شده است.

**بخش چهارم: لغو merge**

اگر هنگام بررسی conflict متوجه شویم که فعلاً نباید شاخه‌ها را ادغام کنیم، از دستور زیر استفاده می‌کنیم:

```bash
git merge --abort
```

این دستور تلاش می‌کند عملیات merge در حال انجام را لغو کند و وضعیت را به قبل از شروع merge برگرداند. با توجه به اینکه در صورت سؤال working tree پیش از merge تمیز بوده است، این دستور روش مناسبی برای کنار گذاشتن عملیات ادغام نیمه‌تمام است.
